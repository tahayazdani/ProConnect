# ProConnect — Project Notes

> Living document. Update this file whenever a phase starts/finishes, a decision changes, or something new is discovered — this is the source of truth for where the project stands, not the conversation history.

## What this is

ProConnect is a **professional-networking dating app** — "Hinge/Tinder, but for professionals, matched on LinkedIn data." Users sign up/sign in with their LinkedIn account; their profile (name, photo, company, location, skills, etc.) is fetched and used to recommend matches based on shared signals (location, company, school, interests). Matched users can follow each other, message, and manage subscription/payment.

## Architecture

Clean-architecture layering across 4 projects (+ tests would go alongside if added later):

| Project | Responsibility |
|---|---|
| `ProConnect.Domain` | Models, request/response DTOs, config POCOs, enums/constants. No dependencies on other projects. |
| `ProConnect.Application` | Business logic (`*Service` classes), FluentValidation validators, `ITokenService`, global `ExceptionHandlingMiddleware`. |
| `ProConnect.Infrastructure` | Repositories (`I*Repository`), HTTP client wrapper, Redis-based cache-aside layer (`Cache` + `ICache`/`RedisCache`). |
| `ProConnect.WebApi` | Controllers, DI wiring (`Program.cs`, `DI/DI.cs`), Serilog logging, Swagger, API versioning, JWT auth. |

Cross-cutting conventions already established in the codebase — follow these for consistency:
- Every service call returns `ProConnectResponse<T>` ([ProConnectResponse.cs](ProConnect.Domain/Response/ProConnectResponse.cs)) — `body`, `message`, `statuscode`, `errormessage`, `errors`, `issuccessfull`.
- Controllers are thin: call the service, `return StatusCode(response.statuscode, response);`. All inherit `BaseController` ([BaseController.cs](ProConnect.WebApi/Controllers/BaseController.cs)) which exposes `CorrelationToken` and `CurrentUserId`.
- Config sections are POCOs under `ProConnect.Domain/Config`, nested inside `ProConnectConfig`, bound via `IOptions<ProConnectConfig>`.
- Repositories for Phases 1-3 (`UserRepository`, `MatchCriteriaRepository`, `MatchRepository`, `SearchRepository`) are real EF Core implementations against Postgres/PostGIS (see Decisions below). Repositories for phases not yet built (Follow, Message, Notification, Subscription/Payment) remain stubbed with `throw new NotImplementedException();` until their phase is implemented — that part of the pattern is unchanged.
- Request/response property names are `snake_case` to match LinkedIn/Proxycurl's own JSON shape.

## Key decisions (don't re-litigate without asking)

- **Database: decided and wired up — PostgreSQL + PostGIS via EF Core, run in Docker.** Superseded the earlier "deferred" state. Docker (via Colima, since Docker Desktop wasn't available) was installed, a `proconnect-postgres` container (Postgres + PostGIS, via docker-compose) and `proconnect-redis` container stood up locally, and the Phase 1-3 repositories (`UserRepository`, `MatchCriteriaRepository`, `MatchRepository`, `SearchRepository`) were implemented for real against it using **EF Core 8 + Npgsql + Npgsql.NetTopologySuite** — no raw SQL/Dapper, per explicit direction; every query is LINQ, translated by the Npgsql EF Core provider.
  - **Location/radius requirement — solved with PostGIS + geocoding, not Redis GEO.** Went with PostGIS (`geography(Point,4326)` column on `users.location`, GIST-indexed) rather than the Redis `GEOADD`/`GEOSEARCH` alternative that was still on the table — keeps geo data next to the rest of the relational user data and inside the same EF Core/LINQ model instead of a second, separately-synced source of truth. Since LinkedIn/harvestapi profiles only carry city/state/country as text (no lat/long), a new **Nominatim/OpenStreetMap geocoding step** (`IGeocodingProvider` → `NominatimGeocodingProvider`, free, no API key) resolves city/state/country into coordinates on signup/profile-update (`UserService.PopulateCoordinates`) before they're written to `location`. `SearchRequest` gained an optional `radius_km`; when set, `SearchRepository.Search` geocodes the search's city/state/country into a center point and orders/filters candidates by `Point.Distance(center)` (translated to PostGIS `ST_Distance`, great-circle meters) — true proximity search, not a bounding-box approximation. Text-based filtering (`EF.Functions.ILike` on city/state/country/industry/company/query) still works independently and can be combined with `radius_km`.
  - **Domain stays EF-free.** New EF-mapped persistence classes live only in `ProConnect.Infrastructure/Persistence/Entity/*` (`UserEntity`, `MatchCriteriaEntity`, `SwipeEntity`, `MatchEntity`), configured via `IEntityTypeConfiguration<T>` classes under `Persistence/Configuration/*` and applied through `ProConnectDbContext.OnModelCreating` (`ApplyConfigurationsFromAssembly`). Repositories map between these and the existing `ProConnect.Domain` request/model types (`UserRequest`, `MatchCriteria`, etc.) via private `ToDomain`/`ToEntity` helpers — `ProConnect.Domain` has zero EF Core dependency, unchanged.
  - **DbContext lifetime**: repositories are registered as Singletons (matches the rest of this codebase's DI style), and `DbContext` isn't thread-safe, so the context is never injected directly. `AddPooledDbContextFactory<ProConnectDbContext>` is registered instead, and every repository method creates/disposes its own short-lived context via `await using var db = await _dbContextFactory.CreateDbContextAsync();`.
  - **Initial migration** (`20260830185435_InitialCreate`) creates `users`/`match_criteria`/`matches`/`swipes` tables, all FKs/indexes (including the GIST index on `users.location` and a unique index on `users.sub`), and enables the `postgis` Postgres extension. Applied to the real `proconnect-postgres` container via `dotnet ef database update` and verified directly via `psql`.
  - **Verified end-to-end** with a throwaway standalone console harness (outside the repo, not committed) that references `ProConnect.Infrastructure` directly and uses a fake `IGeocodingProvider` (fixed SF coordinate, so the radius test doesn't depend on network/Nominatim) — 15/15 assertions passed: signup/get/update round-tripping, match-criteria upsert semantics (insert then update, not duplicate), candidate exclusion (self + already-swiped), swipe/match idempotency regardless of argument order, text search by city/industry, and true-radius search (San Francisco↔Oakland ~13km apart included at a 50km radius, excluded at 5km; NYC ~4130km away excluded at both).
- **Redis: cache everything read-heavy, not just match recommendations.** Explicit direction: whatever the database ends up being, Postgres (or any DB) reads should go through the Redis cache-aside layer by default — search results, match recommendations, profile lookups, etc. `MatchService`'s use of the existing `Cache`/`CacheRegion` pattern ([Cache.cs](ProConnect.Infrastructure/Repository/Cache.cs)) is the template to repeat for every future read-heavy service (Search in Phase 3, Follow lists, Notifications, etc.) — give each its own `CacheRegion` constant and reuse `_cache.Get(key, factory, region)` rather than hitting the DB directly.
- **Match criteria: zero required input, everything optional.** Per explicit direction: don't make users answer onboarding questions like other dating apps. `MatchCriteria` (`ProConnect.Domain/Model/MatchCriteria.cs`) holds only *optional overrides*; `MatchService.ResolveEffectiveCriteria` merges them with defaults derived straight from the user's own LinkedIn profile (city/state/country, industry, interests), so recommendations work immediately with no setup. The one exception is `min_age`/`max_age` — LinkedIn has no dating-age-preference signal, so that genuinely has no profile-derived default and stays unfiltered unless the user sets it explicitly.
- **Profile enrichment: migrated off Proxycurl to `harvestapi/linkedin-profile-scraper` on Apify, behind an `IProfileProvider` adapter.** Superseded decision — Proxycurl (the previous provider) was sued by LinkedIn/Microsoft (alleging it operated fake accounts to access gated data) and shut down permanently in 2025, despite $10M ARR. That's exactly the "the whole system's heart depends on this one vendor" scenario that made an abstraction worth building. See "Profile provider migration" below for the full detail.
- **Auth: our own JWT.** Issued after LinkedIn sign-up/sign-in via `ITokenService`. Bearer tokens, `[Authorize]`-by-default (global fallback policy in `Program.cs` requires authentication on every endpoint unless `[AllowAnonymous]`).
- **Messaging: REST only for now.** No SignalR/real-time in the first pass.
- **Cache TTLs are per-region, not global.** `Cache.Get`/`Cache.Set` ([Cache.cs](ProConnect.Infrastructure/Repository/Cache.cs)) take an optional `TimeSpan? expiry` that overrides `CacheAsideConfig`'s single global timeout for that call. Named policies live in `CacheExpiry` next to `CacheRegion` ([Const.cs](ProConnect.Domain/Const/Const.cs)) — add one per region as new regions get used (e.g. `CacheExpiry.SearchResult` when Phase 3 lands). Don't add a new `_cache.Get(...)` call without picking an explicit expiry for it.
- **No separate "Follow" concept — collapsed into Match, per explicit direction.** Superseded decision (previous bullet used to say Follow/messaging were open, ungated). This app is dating-style (Tinder/Hinge), not a social network — a mutual like already *is* the connection; there's no asymmetric one-way follow on top of it. Phase 4 became "round out the Match domain" instead of a standalone `FollowerController`/`FollowingController`: list your matches, unmatch, and block. See the "Match lifecycle" decision below for full detail. Messaging (Phase 5, not yet built) will be scoped to matched pairs only when it lands, not open to anyone.
- **Match lifecycle: list, unmatch (unilateral), block (mutual invisibility).** `IMatchRepository` gained `GetMatches`/`Unmatch`/`BlockUser`; `MatchController` gained `GET matches`, `DELETE matches/{matchId}`, `POST {targetUserId}/block`.
  - **Unmatch is unilateral** — either side can end a match at any time, no agreement from the other party required (standard for dating apps). `MatchRepository.Unmatch(userid, matchId)` only succeeds if `userid` is actually one side of that match, so a third party can't unmatch a pair they aren't in. Doesn't touch future search visibility — the original mutual-like swipe rows are permanent, so an unmatched pair already stays excluded from each other's `GetCandidates` forever regardless.
  - **Block is mutual, not one-directional** — explicit design call after being asked "if A blocks B, does A still see B, does B still see A, or neither?". Went with *neither*: on a dating app, blocking exists mostly for safety/harassment, so a one-directional block (where the blocked party could still swipe on/message the blocker again) would defeat the point. `MatchRepository.BlockUser(blockerUserId, blockedUserId)` dissolves any existing match between the pair and writes one directional `blocks` row, but `GetCandidates` excludes the *pair* from each other regardless of which side placed the block. New `blocks` table/`BlockEntity` (composite PK `blocker_user_id`+`blocked_user_id`), same defensive FK pattern as `MatchEntity` (`blocker_user_id` cascades, `blocked_user_id` is `Restrict` — two FKs into the same `users` table can't both cascade) — `UserRepository.DeleteAccount` was updated to explicitly purge `blocks` rows (both directions) before deleting the user row, same reasoning as the existing `matches` handling.
  - **Verified** end-to-end against the real Postgres container via a throwaway standalone console harness — 24/24 assertions passed: match listing shows the *other* party's profile on both sides, unauthorized unmatch attempts fail and leave the match intact, unilateral unmatch by either side clears it for both, blocking dissolves an existing match and excludes both directions from `GetCandidates` (confirmed with an isolated D/E pair to rule out "already swiped" as the cause instead of the actual block), and `DeleteAccount` cleanly purges `blocks` rows including for a user on the `Restrict` side of the FK (which would otherwise throw).
- **"Who liked me" — pending incoming likes, scored/filtered the same as recommendations.** Follow-up request after Match lifecycle landed. `IMatchRepository.GetIncomingLikes(userid)` returns everyone who has liked `userid` that `userid` hasn't swiped back on yet (once they respond, either direction, it's no longer "pending" — a reciprocal like already produces a match/swipe row via the normal `Like` flow, a pass resolves it the other way), same `is_active`/mutual-block exclusions as `GetCandidates`. `IMatchService.GetIncomingLikes` reuses the exact same age-filter/scoring/sort logic as `GetRecommendations` via a newly-extracted shared helper (`MatchService.MapToCandidateResponses`) rather than duplicating it, so a person liking one back from this list works identically to liking them from the normal recommendation feed. `MatchController` exposes it as `GET liked-me`. **Deliberately not cached** (unlike `GetRecommendations`'s 15-minute Redis TTL) — a brand-new incoming like should show up immediately, and the query is cheap since it's only scanning people who already liked you, not the whole candidate pool.
- **Recommendations/incoming-likes are paged, and the expensive part (scoring the whole candidate pool) only happens once per cache window, not once per page.** Follow-up request: user asked (1) whether there's a "load X, cache it, don't re-hit the DB every time" concept, and (2) what the refill plan is once a client is almost through its current batch (dating-app swipe-deck UX: hand the client a page at a time, not the entire pool in one response). Design, in the user's own words after I proposed it: cache the *entire* scored/sorted candidate list once (already what `GetRecommendations` did before this change, just unpaginated), then let each page request slice that cached list server-side instead of recomputing/re-querying — so paging through an already-fetched batch costs zero extra DB/scoring work. New shared `MatchCandidatePageRequest` (`page`, `pagesize`, `refresh`) / `MatchCandidatePageResponse` (`results`, `total_count`, `page`, `pagesize`, `has_more`), used by both `GetRecommendations` and `GetIncomingLikes` — mirrors `SearchRequest`/`SearchResponse`'s existing `page`/`pagesize` convention (same `[1,50]` `pagesize` bound via a new `MatchCandidatePageRequestValidator`, registered in `Program.cs` the same way `SearchRequestValidator` is).
  - **`GetRecommendations`**: `MatchService.BuildPage` slices the cached full list in memory (`Skip`/`Take`) rather than pushing pagination into the DB query — deliberately different from `SearchRepository.Search`'s SQL-level `Skip`/`Take`, because the whole point here is that scoring the full pool is the expensive part and should happen once per `CacheExpiry.MatchRecommendation` window (15 min), not once per page.
  - **The "refill" answer**: `request.refresh = true` bypasses (deletes, then repopulates) the cached list before paging, for when a client has paged past the last page (`has_more = false`) and wants a fresh recompute immediately instead of waiting out the 15-minute TTL — the intended client pattern is to prefetch the next page proactively (e.g. once the user is ~10 cards from the end of their current batch) and fall back to `refresh = true` once truly out of cached candidates.
  - **`GetIncomingLikes`** gets the same paged response shape for API consistency, but `refresh` is a no-op there since that endpoint was never cached to begin with (see the "Who liked me" decision above).
  - **Verified** against the real Postgres + local Redis containers via a throwaway standalone console harness driving the real `MatchService` (not just the repository) — 18/18 assertions passed: paging 12 seeded candidates in pages of 5 returns 5/5/2 with correct `has_more` on each and the union of all pages exactly matches the seeded set with no duplicates; adding a 13th candidate mid-test and re-fetching without `refresh` still shows the stale cached count of 12 (proving no DB re-hit); the very next call with `refresh = true` immediately shows 13 and includes the new candidate; `GetIncomingLikes` pagination (5 likers, pages of 3 → 3/2 with correct `has_more`) and its lack of caching (a brand-new liker shows up with no `refresh` flag at all) both held.
- **`GetRecommendations` caches a bounded per-user window into a SQL-filtered candidate query, not the whole scored pool — superseded decision, scale-motivated.** Follow-up direction after the point above shipped: caching the *entire* candidate pool per user (previous design) scales with total active-user count, not flat — at real scale, every user's Redis entry would hold every candidate that ever matched their criteria, recomputed by loading the *whole* pool into memory and scoring it in C#. Two changes, agreed step by step:
  - **Age/industry/location filtering moved from in-memory scoring into SQL `WHERE`/`ORDER BY`.** `IMatchRepository.GetCandidates` now takes `(userid, MatchCriteria criteria, int offset, int limit)` instead of just `userid`, and a new `IMatchRepository.CountCandidates(userid, criteria)` reports the total matching row count without materializing it. Age range filters on a new generated `users.birthdate` column (`GENERATED ALWAYS AS (make_date(birth_year, birth_month, birth_day)) STORED`, indexed) instead of loading every candidate's `birth_year/month/day` and computing age in C#; the generated-column semantics (NULL propagates if any input is NULL) match the old "unknown birthdate excludes from an age-filtered query" behavior for free. Industry became a **hard exact-match filter** (via a new generated, indexed `users.industry_normalized = lower(industry)` column) instead of a soft +25 score bump — explicit correction after being asked "why would we show someone outside the industry they asked for at all instead of just ranking it lower," made symmetric with how age already worked (both pass-through when unset, both hard-exclude when set). `MatchCriteria` gained `radius_km` (mirrors `SearchRequest.radius_km`) with a 3-tier location priority, per explicit direction: **(1) `radius_km` set → PostGIS `Point.Distance` radius filter, highest priority; (2) no radius but any of city/state/country set → hierarchical `ILike` filter on whichever are set (not mutually exclusive — city+state+country can combine); (3) neither → no location filter at all, just an `ORDER BY distance` tiebreaker off the caller's own geocoded location so nearby candidates still surface first** when nothing else differentiates them. `MatchService.MapToCandidate` (the recommendations-only candidate mapper) now only scores *interests* — city/state/country/industry/age scoring was removed for this path since SQL already guarantees every row satisfies them; `ScoreCandidate`/`MapToCandidateResponses`/`IsWithinAgeRange` are untouched and still used as-is by `GetIncomingLikes`/`GetSeenProfiles`, which pull from small non-scaled pools (people who liked you / people you passed on) where in-memory scoring was never the bottleneck.
  - **Redis now caches a bounded, incrementally-grown *window* into that filtered query, not the whole pool.** New `MatchRecommendationBatch` (`Items`, `NextOffset`, `ExhaustedPool`, `TotalCount`) replaces the flat `List<MatchCandidateResponse>` that used to sit behind `RecommendationCacheKey`. `MatchService.GrowBatch` fetches `RecommendationBatchFetchSize` (100) rows starting at `NextOffset`, appends them, and refreshes `TotalCount` via `CountCandidates` — so a user's cache entry stays flat-sized regardless of how many people match their criteria pool-wide. **The refill is genuinely invisible to the user in the common case**: once fewer than `RecommendationRefillThreshold` (20) unread items remain in the cached window after serving a page, `TriggerBackgroundRefill` fires a detached `_ = Task.Run(...)` that grows the batch in Redis *after* the response has already been returned — safe with no scoped-disposal risk because every Match/Cache service in this app (`MatchService`, `MatchRepository`, `Cache`, `RedisCache`, `UserRepository`) is registered `Singleton` and each repository call opens/closes its own short-lived `DbContext` via `IDbContextFactory`, confirmed by reading `Program.cs`/`DI/DI.cs` before committing to the fire-and-forget pattern. The *only* path that can make a caller wait on `GetCandidates` is a genuine cold start or a client jumping straight to a page not yet covered by the cached window — everything else is either an in-memory slice or happens after the response went out. `ExhaustedPool` (set once a `GetCandidates` fetch returns fewer rows than requested) is the empty-pool sentinel — once true, later calls stop re-querying the DB for more until the cache entry expires or `request.refresh`/a criteria change invalidates it, same as before.
  - **Verified** against the real Postgres + local Redis containers via a throwaway standalone console harness driving the real `MatchService`/`MatchRepository` (not mocks) — 28/28 assertions passed: age range hard-excludes too-young/too-old/unknown-birthdate candidates while including in-range ones; industry hard-excludes a mismatched industry; all three location tiers verified directly (radius includes a ~2km candidate and excludes a ~560km one; city/state text filters correctly scope by whichever fields are set; the no-location fallback includes everyone matching other criteria but orders a nearer candidate before a farther one); `CountCandidates` matches `GetCandidates`' actual row count; `GetRecommendations`' `total_count` matches an independent `CountCandidates` call against the same effective (profile-merged) criteria; paging through every page of a `GetRecommendations` session yields exactly `total_count` unique candidates with no duplicates; a candidate added mid-session doesn't appear without `refresh` (proving the cached window, not a live query, is being served) but appears immediately with `refresh = true`, with `total_count` increasing by exactly one.
  - **`radius_km` needed a real DB column, not just a Domain/Request/Response field** — `MatchCriteriaEntity`/`MatchCriteriaRepository` were missing it entirely (an oversight caught while smoke-testing, before it ever reached a real request), so a second migration (`AddRadiusKmToMatchCriteria`) added the persisted column; the original `AddBirthdateAndIndustryGeneratedColumns` migration only covered the generated `users` columns.
- **Passed profiles are permanently excluded from the regular deck, with an explicit "see profiles you already passed on" recovery endpoint — not a silent resurfacing.** Follow-up request, prompted by describing how Hinge's swipe-deck end-state works: it prefetches on open, stops with an explicit "no more profiles" state once the deck runs dry, and offers two recovery paths — revisit already-seen profiles, or change criteria. "Change criteria" was already fully wired (`UpdateCriteria` invalidates the cached recommendation list, so the next `GetRecommendations` call recomputes automatically) — no changes needed there. The "revisit passes" half was a real gap: `GetCandidates` already permanently excludes anyone in `swipes` (like or pass) and the user explicitly confirmed passed profiles should **never** reappear in the regular deck on their own. New `IMatchRepository.GetPassedCandidates(userid)` / `MatchRepository.GetPassedCandidates` — the mirror image of `GetCandidates`'s `alreadySwiped` exclusion: pulls only `Pass` swipes (not `Like` — a liked-but-unreciprocated profile has no path back into "seen", and a mutual like is already a match), same `is_active`/mutual-block exclusions as `GetCandidates`/`GetIncomingLikes`. New `IMatchService.GetSeenProfiles`/`MatchService.GetSeenProfiles` reuses the same `MapToCandidateResponses`/`BuildPage` helpers as `GetRecommendations`/`GetIncomingLikes`, so it gets the same age-filter/scoring/paging behavior and response shape (`MatchCandidatePageRequest`/`Response`) for free. **Deliberately not cached**, same reasoning as `GetIncomingLikes` — it's an on-demand recovery action, not part of the hot swiping path, so `refresh` is a no-op there too. `MatchController` exposes it as `GET seen`. Liking someone off this list needs no special handling — the existing `Like`/`Pass` endpoints work on any `targetUserId` regardless of which list it came from, and `RecordSwipe` already upserts (flips the existing `Pass` row to `Like`).
  - **Verified** against the real Postgres container via a throwaway standalone console harness driving the real `MatchService` — 24/24 assertions passed: the seen list contains only profiles the user passed on (not untouched, liked, blocked, or deactivated ones, even though all were passed on where applicable); the regular deck (`GetCandidates`) simultaneously excludes every passed/liked/blocked/deactivated profile while still surfacing the untouched one; liking a profile surfaced from the seen list succeeds and immediately removes it from the seen list on the next call while leaving other passed profiles in place; and the seen list itself pages correctly (5 passed profiles in pages of 3 → 3/2 split, correct `has_more`, no duplicates across pages).
- `AccountController` = the user's own profile + (eventually) an aggregate settings view. `Payment`/`Subscription`/`Match` own their specific domains.
- **Account removal is two distinct features, not one — deactivation (temporary, reversible) and deletion (permanent, irreversible).** Initially built as a single soft-delete flag; corrected after explicit direction that these need to behave like Instagram's "deactivate temporarily" vs. "delete account permanently": deactivation keeps all data and comes back automatically on next sign-in, deletion physically erases everything and cannot be undone. Both live behind `IUserRepository`/`IUserService`, self-service only (no admin/role system yet to act on someone else's account).
  - **Deactivation — `is_active` flag, nothing is deleted.** `UserRequest`/`UserEntity` both carry `is_active` (default `true`, DB column also defaults `true`, migration backfills every existing row as active, indexed as `IX_users_is_active`). New signups are always forced active (`UserRepository.ToEntity` sets it explicitly, ignoring whatever a caller might pass). Turned off via `IUserRepository.Deactivate(userid)` → `IUserService.DeactivateAccount` → `POST api/account/v1/deactivate` (idempotent; returns `false` only if the userid doesn't exist at all). **Enforced everywhere a user can be looked up or listed**: `UserRepository.GetById`/`GetBySub`, `MatchRepository.GetCandidates`, `SearchRepository.Search` all filter `is_active == true` — a deactivated user is invisible to everyone, including themselves (their own `GetProfile`/`UpdateProfile`/`SystemAuthentication` calls fail with "User not found" since they go through `GetById`).
  - **Reactivation is automatic on sign-in, not a separate endpoint — this is the Instagram-style part.** `UserService.LinkedInAuthentication` now looks the user up via a new `IUserRepository.GetBySubForAuthentication` (deliberately *not* filtered by `is_active`, unlike the regular `GetBySub` used everywhere else) so a deactivated account is still found instead of treated as "never signed up." If found and `is_active == false`, it calls the new `IUserRepository.Reactivate(userid)` before issuing a token — signing back in *is* the reactivation action, with no dedicated "reactivate" endpoint for the user to separately hit.
  - **Deletion — genuinely irreversible, physically removes every row tied to the user.** New `IUserRepository.DeleteAccount(userid)` → `IUserService.DeleteAccount` → `DELETE api/account/v1/profile` (HTTP DELETE now maps to the thing that actually deletes the resource, not to deactivation — see below for why the route assignment flipped). Deletes `swipes` (both directions), `matches` (both sides), and `match_criteria` for the user, then the `users` row itself, explicitly and in that order inside a single DB transaction — not relying purely on FK cascade config, since `matches.userid_b` is intentionally `OnDelete(Restrict)` (not `Cascade`, see `MatchEntityConfiguration`) and a bare "delete the user row" would fail with a FK violation for any match where this user is `userid_b`. Deleting children first sidesteps that regardless of each FK's configured behavior. Uses EF Core's `ExecuteDeleteAsync` (bulk `DELETE`, no loading rows into memory first).
  - **Route naming, changed from the first pass**: originally `DELETE api/account/v1/profile` meant *deactivate*, which turned out to be a semantic mismatch once real deletion existed too — HTTP DELETE should mean "this resource is gone," not "flip a flag." Deactivation moved to `POST api/account/v1/deactivate` (an explicit action, not idempotent-resource-deletion semantics); `DELETE api/account/v1/profile` now means what it says. No real users/clients existed against the old mapping yet, so this was a clean rename, not a breaking migration.
  - **Explicit scope limits, still not built**: (1) no admin/role system, so neither deactivation nor deletion can be done to someone else's account; (2) no request-level/auth-middleware enforcement that actively blocks a deactivated user's already-issued JWT mid-flight — the practical effect is their profile becomes unreachable and they drop out of every match/search result, but an old token isn't actively revoked, it just can't do anything useful once `GetById` starts filtering it out.
  - **Verified** end-to-end against the real Postgres container via a throwaway standalone console harness — 20/20 assertions passed: deactivate → confirm invisible via `GetById`/`GetBySub` but still found (and reported `is_active=false`) via `GetBySubForAuthentication` → reactivate → confirm visible again everywhere including match candidates → reactivate is `false` for a nonexistent userid; then, for delete: seeded a user with match criteria, a swipe, and a mutual match, confirmed those rows exist, called `DeleteAccount`, confirmed the user row and every referencing swipe/match/match_criteria row are physically gone, confirmed `DeleteAccount` returns `false` both for a nonexistent userid and for calling it again on an already-deleted one.
- **Logging: service layer owns it, infrastructure just propagates.** Decided explicitly to avoid the same exception getting logged twice (once low in the stack with no business context, once higher up) as the codebase grows. Convention going forward: repositories and other infra code (`HttpClientUtilities`, EF Core repositories) **do not** call `_logger.LogError` in their `catch` blocks — they either don't catch at all, or catch only to clean up/rethrow, with a comment pointing here instead of a duplicate log line. The `Application` layer's `*Service` classes are the primary logging point — every service method's `catch (Exception ex)` now logs with real business context (which user id, which operation, which target/params) before rethrowing, e.g. `_logger.LogError(ex, $"Swipe ({action}) failed for userid '{userid}' -> targetUserId '{targetUserId}'.")`. `ExceptionHandlingMiddleware` stays as the final safety net — it still logs too, but that's a generic catch-all for anything that somehow reaches it unlogged, not the primary logging point anymore.
  - **Deliberate exception: `Cache`/`RedisCache` (`ProConnect.Infrastructure/Repository/Cache.cs`).** Left untouched, on purpose. `Set`/`Delete` **swallow** Redis failures entirely after logging (cache-aside resiliency — a Redis outage shouldn't take down a read that could've just hit the DB), which means there's no exception left for any service-layer `catch` to ever see or log — stripping the log there would make Redis failures completely invisible, not just move where they're logged. `Get`'s log-and-rethrow is kept for the same reason: it's infra-level cache resiliency logic, not a business exception path, so it doesn't fit the "service layer logs business context" rule cleanly either way.
- **100M-user-scale audit — five concerns identified and fixed together, per explicit direction ("fix all these concerns together now").** Follow-up after being asked directly whether the system, as built, would hold up at 100M users, and if not, what needed to change. Ranked by severity and addressed in one pass:
  - **`GetIncomingLikes`/`GetPassedCandidates`/`GetMatches` moved to real DB-level pagination**, matching the pattern `GetCandidates`/`CountCandidates` already used. Previously these three fully materialized their entire result set (every incoming like, every passed profile, every match) into memory before slicing a page out of it in C# — fine at prototype scale, not at scale where a popular/long-tenured user's list could be huge. `IMatchRepository.GetIncomingLikes`/`GetPassedCandidates` now take `(userid, criteria, offset, limit)` with matching `CountIncomingLikes`/`CountPassedCandidates`; `GetMatches` takes `(userid, offset, limit)` with `CountMatches`. Query-building was factored into shared, reusable helpers (`MatchRepository.ApplyAgeFilter`, `BuildIncomingLikesQuery`, `BuildPassedCandidatesQuery`) so the paged fetch and its count call always see identical filters. **Trade-off, made deliberately and documented in code**: sort order for `GetIncomingLikes`/`GetSeenProfiles` changed from "highest relevance score first" (only possible by scoring the *entire* pool in memory, which is exactly the thing being eliminated) to "most-recent-swipe-first" (`ORDER BY swiped_at_utc DESC` in SQL) — the per-item relevance score is still computed and returned for display, just no longer used for ordering. `MatchService` gained a shared `BuildPageFromScoredItems` helper for this; the old full-materialize-then-slice `MapToCandidateResponses`/`BuildPage` helpers were removed as dead code once nothing called them anymore, along with `IsWithinAgeRange`/`CalculateAge` (age filtering was already fully SQL-side via `ApplyAgeFilter`, same generated `birthdate` column `GetRecommendations` already used — these three endpoints just hadn't been migrated to it yet). New `MatchSummaryPageResponse` (Domain/Response) gives `GetMatches` the same paged-response shape (`results`/`total_count`/`page`/`pagesize`/`has_more`) as the other list endpoints; `IMatchService.GetMatches`/`MatchController.GetMatches` updated to take `MatchCandidatePageRequest` accordingly.
  - **`UserRepository.GetById` cache-aside**, closing the gap where `MatchService.ResolveEffectiveCriteria` — hit on *every* recommendations/incoming-likes/seen/criteria request — called it uncached on every single one. New `CacheRegion.USERPROFILE` / `CacheExpiry.UserProfile` (10 minutes — deliberately shorter than `PERSONPROFILE`'s 7 days, which caches externally-scraped LinkedIn data that barely changes; a user's own profile row, `is_active` flag included, needs to go stale much sooner). Invalidated proactively (not just left to the TTL) on every write path: `Update`, `Deactivate`, `Reactivate`, `DeleteAccount`. A deactivated/nonexistent user (`null` result) is deliberately never cached in the first place — `Cache.Set` is already a no-op for `null` data — so deactivation is reflected on the very next read instead of waiting out the TTL.
  - **`matches`/`swipes` indexes reviewed, no change needed for the `OR` query pattern.** An earlier automated audit pass had flagged `matches.userid_a == userid || userid_b == userid` (used by `GetMatches`) as needing a new composite index. Checked directly against `MatchEntityConfiguration` before acting on that: `userid_a` and `userid_b` already each have their own separate index, and Postgres can combine two single-column indexes for an `OR` predicate via a bitmap index scan (`BitmapOr`) just as effectively as a purpose-built composite one would — confirmed no new index was actually needed rather than adding a redundant one on faith.
  - **`swipes`/`matches` table partitioning — evaluated, deliberately deferred, not applied.** At real 100M-user scale these two tables are the highest-row-count, highest-write-rate tables in the schema and are the most likely eventual candidates for partitioning (e.g. hash-partitioned by `userid`, or range-partitioned by `swiped_at_utc`/`matched_at_utc` for time-based archival). Not done now: partitioning an existing live table is a structural, higher-risk schema change (requires a maintenance-window migration strategy — new partitioned table + backfill + cutover, not a simple `dotnet ef migrations add`) that shouldn't be applied speculatively via an automated pass without a dedicated, explicitly-approved migration plan. Flagged here as planned future infra work, not silently skipped.
  - **Npgsql connection pool sizing made explicit instead of relying on library defaults.** New `DataBaseConfig.minpoolsize`/`maxpoolsize`/`connectionidlelifetimeseconds` (all nullable — unset means "use the default"), applied in `Program.cs` via `NpgsqlConnectionStringBuilder` on top of the per-environment connection string, only when the string doesn't already specify pooling behavior itself (an explicit `Pooling=false`/custom values in a future environment's connection string always wins over these). Default max raised from Npgsql's built-in 100 to `Math.Max(existing, 100)` as a floor, not a fixed value — at higher instance counts/QPS, a silent, easy-to-forget default becomes the limiting factor before Postgres itself does.
  - **GIN trigram (`pg_trgm`) indexes added for `SearchRepository.Search`'s leading-wildcard `ILIKE`.** `SearchRepository.Search` matches `full_name`/`headline`/`occupation`/`company`/`industry`/`city`/`state`/`country` with `ILIKE('%term%')` — a leading wildcard a plain B-tree index can't accelerate at all, forcing a full table scan on every search. `pg_trgm` extension registered via `modelBuilder.HasPostgresExtension("pg_trgm")`; all 8 columns got a `HasMethod("gin").HasOperators("gin_trgm_ops")` index (migration `AddTrigramSearchIndexes`). Doesn't touch `MatchRepository.GetCandidates`'s industry/city/state/country filters — those are exact (no-wildcard) matches, already served by the `industry_normalized` btree index or cheap enough unindexed given they're always combined with other hard filters first.
  - **Verified** against the real Postgres + local Redis containers via a throwaway standalone console harness (outside the repo, not committed) driving the real repositories directly — 17/17 assertions passed: `GetIncomingLikes`/`GetPassedCandidates` paginate correctly (5 seeded rows in pages of 3 → 3/2 split, no overlap, most-recent-swipe-first order confirmed against staggered timestamps) with matching `CountIncomingLikes`/`CountPassedCandidates`; `GetMatches` pages correctly and resolves the other party regardless of which side (`userid_a` or `userid_b`) the current user is on, confirming the bitmap-OR index reasoning actually holds at the query-result level, not just in theory; `UserRepository.GetById` serves a stale cached value after an out-of-band direct DB write (proving the cache is genuinely being hit, not bypassed), then reflects the fresh value immediately after a repository `Update` call (proving invalidation works); and `GetCandidates`/`CountCandidates` (untouched by this change) still return a consistent pool as a regression check. `dotnet build` — 0 errors, no new warnings. Migration applied to the real `proconnect-postgres` container and schema verified directly via `psql` (`pg_trgm` extension present, all 8 `IX_users_*` GIN/`gin_trgm_ops` indexes present).
- **Messaging (Phase 5) — conversation model keyed directly off `matchid`, no separate conversations table.** Five design decisions made unilaterally (per explicit "lets do it" direction, after the open questions were posed but not individually answered), grounded in existing codebase conventions rather than guessed from scratch:
  - **No `conversations` entity.** A `matches` row already uniquely identifies the two participants and already gets hard-deleted on unmatch (`MatchRepository.Unmatch`) — introducing a separate conversation entity would just be a redundant 1:1 shadow of `matches` with no behavior of its own. `messages.matchid` points straight at `matches.matchid`; "the conversation for this match" is just "the messages with this `matchid`," computed, not stored.
  - **Content scope is plain text only, v1.** `MessageRequest.content` is a plain `string`, capped at 2000 chars (`MessageRequestValidator`, same `WithErrorCode(ErrorCode.VALIDATION.ToString())` pattern as every other validator) — no attachments/images/rich content, matching how little the rest of the app's write paths currently support beyond plain fields.
  - **Read receipts are a side effect of `GetMessages`, not a separate endpoint.** Opening/paging a conversation *is* "reading" it — `MessageService.GetMessages` calls `MessageRepository.MarkAsRead` (bulk `ExecuteUpdateAsync`, setting `is_read=true`/`read_at_utc=now` only for the *other* participant's unread messages, never your own) before building the page, so the very same response that triggers the read already reflects the just-applied read state — no second round-trip needed to see it. No `PATCH .../read` endpoint exists or is planned.
  - **Unmatch cascade-deletes messages for free, via the FK, not application code.** `messages.matchid`'s FK is `OnDelete(Cascade)` (mirroring the established two-FK pattern used elsewhere in this schema — `senderuserid`'s FK to `users` is `Restrict`, since Postgres/EF Core can't cascade two FKs into the same table); `MatchRepository.Unmatch` already hard-deletes the `matches` row via `ExecuteDeleteAsync`, so unmatching transitively wipes every message for that match with zero new code. Checked `UserRepository.DeleteAccount`'s existing deletion order (Swipes → Matches → Blocks → MatchCriteria → Users) directly rather than assuming — matches are already gone before the `users` row is deleted, so messages are transitively gone too and `DeleteAccount` needed **no changes**.
  - **Endpoint shape**: `GET/POST api/message/v1/{matchId}` on a new `MessageController` (thin, same `StatusCode(response.statuscode, response)` pattern as `MatchController`). `GetMessages` takes `[FromQuery] MessagePageRequest` (`page`/`pagesize` [1,50] — its own type rather than reusing `MatchCandidatePageRequest`, since there's no `refresh`/cache concept for messages, which are deliberately never cached) and returns `MessagePageResponse` (`results`/`total_count`/`page`/`pagesize`/`has_more`, same shape/`has_more` formula as every other paged endpoint). Both endpoints enforce the sender/reader is actually one of the match's two participants (`MessageRepository.IsParticipant`, same shape of check as `MatchRepository.Unmatch`'s ownership guard) and return the same soft-error `"Match not found."` convention used elsewhere for a missing/foreign matchId — `statuscode` stays at its default 200, only `issuccessfull`/`errormessage` signal the failure. Most-recent-first ordering (`ORDER BY sent_at_utc DESC, messageid DESC`), mirroring `GetMatches`.
  - **Verified** against the real Postgres container via a throwaway standalone console harness — 20/20 assertions passed: send/receive a message between two matched users; a non-participant is rejected with the same "Match not found." shape on both send and read; empty/whitespace content is rejected; reading a conversation marks only the other participant's messages read (never the reader's own) and the very same `GetMessages` response already reflects the updated `is_read=true` state with no second call needed; pagination (7 seeded messages, pages of 3 → 3/3/1 split, correct `has_more` at each boundary, no overlap, most-recent message first); and unmatching cascade-deletes every message for that match with zero extra application code. `dotnet build` — 0 errors, no new warnings. Migration `AddMessages` applied to the real `proconnect-postgres` container and schema verified directly via `psql \d messages`.
- **Messaging (Phase 5) — SignalR added as a real-time push layer on top of the existing REST, not a replacement.** Follow-up after being asked directly what messaging technology was used and whether it should be SignalR; the recommended option (of two presented) was approved: keep `MessageController`'s `GET`/`POST` exactly as-is (send, page history, read-receipt-on-GET all unchanged) and add SignalR purely so new messages/read-state changes reach the other participant live instead of requiring another poll.
  - **New `MessageHub` (`ProConnect.WebApi/Hubs/MessageHub.cs`), mapped at `/hubs/messages`.** Clients call `JoinConversation(matchId)`/`LeaveConversation(matchId)` to join/leave a per-match SignalR group (`"match-{matchId}"`); `JoinConversation` re-checks `IMessageRepository.IsParticipant` (same ownership check `MessageService` already does) and throws `HubException("Match not found.")` for a non-participant — a `HubException`'s message is specifically designed by SignalR to reach the client even with `EnableDetailedErrors` off, so this soft-error text surfaces exactly like the REST one does. No explicit `[Authorize]` attribute needed - the hub is covered by the same global fallback policy (`RequireAuthenticatedUser()`) as every REST controller.
  - **New `IMessageNotifier` seam (`ProConnect.Application.Interface`), implemented by `SignalRMessageNotifier` (`ProConnect.WebApi/Hubs`).** Same reasoning as `IProfileProvider`'s vendor-adapter seam: `MessageService` (Application layer) depends on this abstraction, not on SignalR/WebApi directly - `ProConnect.Application.csproj` has no SignalR dependency at all, only `ProConnect.WebApi` does, where the real `IHubContext<MessageHub>` lives. `MessageService.SendMessage` pushes a `"NewMessage"` event (the full `MessageResponse`) to the match's group right after persisting; `MessageService.GetMessages` pushes a `"MessagesRead"` event (`matchid`/`readeruserid`/`read_count`/`read_at_utc`) right after `MarkAsRead`, but only when `MarkAsRead`'s now-returned row count is `> 0` (re-opening an already-read conversation stays silent, no pointless push). `IMessageRepository.MarkAsRead`'s signature changed from `Task` to `Task<int>` to support this.
  - **Pushes are deliberately best-effort - a notify failure can never fail the REST call that already durably persisted the write.** Both call sites wrap the `IMessageNotifier` call in its own try/catch that logs a warning and swallows, rather than the usual "log and rethrow" convention every other service method catch block uses - same reasoning already documented for `Cache`/`RedisCache.Set` swallowing Redis failures: the message/read-state is already the source of truth in Postgres, so losing the live push just means the other participant sees the change on their next `GET` instead of instantly, nothing is actually lost.
  - **JWT auth extended to cover the WebSocket handshake, which can't set a normal `Authorization` header.** `Program.cs`'s `AddJwtBearer` gained an `OnMessageReceived` event that reads an `access_token` query-string parameter and only honors it for request paths under `/hubs` - every other (REST) request still requires a real `Authorization` header, unchanged.
  - **No new NuGet package for the server side** - SignalR's server library ships inside the `Microsoft.NET.Sdk.Web` shared framework already targeted by `ProConnect.WebApi`; only `builder.Services.AddSignalR()` + `app.MapHub<MessageHub>("/hubs/messages")` were added to `Program.cs`.
  - **Verified** against a real running instance of the WebApi host (not just the repository/service layer in-process, since a live `IHubContext` only exists inside a hosted app) plus the real Postgres container, via a throwaway standalone console harness using `Microsoft.AspNetCore.SignalR.Client` and hand-minted JWTs (via the real `TokenService` + the actual `dotnet user-secrets` JWT config, bypassing the LinkedIn OAuth flow) — 15/15 assertions passed: two participants' hub connections connect and join the match's group; a non-participant's `JoinConversation` is rejected with a message containing "Match not found."; sending a message via the existing REST `POST` triggers a live `NewMessage` push to the other participant's connection with the correct `matchid`/`content`; reading via the existing REST `GET` triggers a live `MessagesRead` push to the sender's connection with the correct `matchid`/`readeruserid`/`read_count`; and immediately re-reading (nothing new to mark read) pushes nothing a second time. `dotnet build` — 0 errors, no new warnings.

## Profile provider migration (Proxycurl → harvestapi/Apify)

- **Why**: Proxycurl was sued by LinkedIn/Microsoft in Jan 2025 (fake-account allegations) and shut down by mid-2025. Its would-be successor, Enrich Layer, publishes no reliability/legal-compliance info. `harvestapi/linkedin-profile-scraper` on Apify was chosen instead: ~5-10x cheaper ($0.004/profile vs. Enrich Layer's $0.02-0.30), strong verifiable usage (61k+ users, 4.77★), "no cookies/account required" (a different, likely lower-risk technique than what specifically got Proxycurl sued), and marketplace redundancy if this actor breaks or its maintainer stops maintaining it.
- **Architecture**: `IProfileProvider` ([IProfileProvider.cs](ProConnect.Infrastructure/Interface/IProfileProvider.cs)) is the new seam — `UserService` depends on it, not on any vendor directly, so a future provider swap is a DI registration change, not a rewrite. `HarvestApiProfileProvider` ([HarvestApiProfileProvider.cs](ProConnect.Infrastructure/Provider/HarvestApiProfileProvider.cs)) calls Apify's synchronous `run-sync-get-dataset-items` endpoint (returns scrape results directly in the HTTP response, up to a 300s ceiling — fits the existing synchronous signup flow) and maps the vendor's raw JSON shape (`HarvestApiProfileResult` — mirrors the vendor's exact field names, verified field-by-field against a real captured API response) into the app's existing, vendor-agnostic `PersonProfileResponse`. `PersonProfileResponse`/`UserRequest`/`SignUpResponse`/`MatchService` needed **zero changes** — that's the adapter doing its job.
- **Data mapping notes** (things a future reader might otherwise think are bugs):
  - `industry` has no source field anywhere in this provider's payload → left `null`. `MatchService`'s industry-match scoring tier is inert for profiles sourced this way until a better source is found.
  - `interests` is mapped from `topSkills`, not the vendor's own `interests` field — the vendor's `interests` means something else entirely (companies/people/groups the person follows on LinkedIn, a deeply nested structure), not personal interest topics. `topSkills` is the closer analog for a professional-matching signal anyway, given ProConnect's whole premise.
  - `gender`/`birth_date` are always `null` from any LinkedIn-based provider (LinkedIn doesn't expose either) — unchanged from before; `UserService.SignUp` fills both from the signup request as it always has.
  - Experience/education dates only carry month+year (day defaults to `1`) — harmless, since this data is never fed through date validation (only the top-level `birth_date` is).
  - Default scrape mode is `"Profile details no email"` ($4/1k, not $10/1k) — cheaper, and `UserService.SignUp` already has a fallback to the client-supplied email when the provider doesn't return one.
- **Live-verified with a real token.** Ran one real, billed call (~$0.004) end-to-end via a scratchpad-only harness (bypassing the web app, since Redis was unreachable from this sandbox at the time — see below) — response mapped correctly, matched what was seen testing in Apify's UI. **Observed latency: ~9.5s per profile**, not the ~2s originally quoted for Enrich Layer — comfortably under Apify's 300s sync-call ceiling, but worth knowing for anyone timing the signup flow.
- **Token location: moved back to `appsettings.json`, deliberately, temporarily.** Was briefly in `dotnet user-secrets`, but the explicit decision is to keep it in the committed file for now and move to **Azure Key Vault** later rather than user-secrets as the intermediate step. Tracked as an open item below, not a mistake to "fix" back to user-secrets.
- **New endpoint**: `GET /api/user/v1/linkedinprofile?publicIdentifier=...` ([UserController.cs](ProConnect.WebApi/Controllers/UserController.cs)) scrapes and returns a profile standalone, without signing anyone up — backed by `IUserService.GetLinkedInProfile`. Kept behind auth (no `[AllowAnonymous]`) since every call costs real money against the scraper API; that's the only endpoint-level guard against abuse right now.
- **Environment note, not a bug**: the configured Redis host (`redis-10100.ctcldevrds.msoclient.com` in `appsettings.json`) appears to be reachable only from a corporate network/VPN — every controller action fails with a Redis connection error when it isn't reachable, since `UserService` → `Cache` → `RedisCache` sits in the DI graph for every request regardless of whether that particular action touches the cache. Not something to fix from here; just know that if the whole app 500s including `/ping`, this is almost certainly why.

## Frontend integration notes (no frontend exists yet — read this before building one)

Nothing here is implemented or agreed with a frontend yet; these are recommendations based on how the backend is built, to revisit once frontend work actually starts.

- **Swipe-deck paging/prefetch strategy for `GET recommendations` / `GET liked-me` / `GET seen`.** All three return the same `MatchCandidatePageResponse` shape (`results`, `total_count`, `page`, `pagesize`, `has_more`). Two distinct moments matter, and they should be handled differently:
  - **Prefetching the next page** (cheap — server-side it's just an in-memory slice of the already-cached full list, no DB/rescoring work): don't wait until the user's local deck is empty. Once the client has ~5-10 cards left in the currently-loaded batch, fetch the next page in the background so it's ready before the user runs out. The client can track this itself from `total_count` (returned on the very first call) vs. how many cards it's shown so far — no extra server signal needed. Suggested starting point: `pagesize=20`, prefetch trigger at 5-10 remaining.
  - **Actually running out** (`has_more: false` on the last page): this is the only point where a real recompute is useful — the cached list is exhausted, so the only way more candidates could exist is if the 15-minute TTL genuinely has something new (new signups, newly-eligible users). Fire one `refresh=true` call right when `has_more` first flips to `false`, *before* showing an empty state, as a last check for anything new. Don't recompute on every swipe or mid-deck — swipes are already excluded permanently via `RecordSwipe`/`GetCandidates`, so a mid-deck recompute can't surface anything paging forward wouldn't already show.
  - If the post-refresh call is still empty, that's the real end-of-deck state — surface the two recovery options: `GET seen` (previously-passed profiles) and/or change criteria via `PUT criteria` (which already invalidates the cache automatically, so the very next `GET recommendations` reflects it).
- **`refresh` is a no-op on `GET liked-me` and `GET seen`** (neither is cached — see their "Key decisions" entries above) — no need to ever set it there, though it's harmless if sent.
- **Full detail/rationale** for all of the above lives in the "Recommendations/incoming-likes are paged" and "Passed profiles are permanently excluded from the regular deck" entries under "Key decisions" above — read those first if anything here is unclear.
